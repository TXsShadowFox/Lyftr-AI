# 4. EXACT API CONTRACT

Implement the three endpoints specified in the PDF.

## GET /health

Return HTTP 200 only when:

- Application is running.
- SQLite is reachable.
- Key pool is configured and loaded.
- At least two API keys are configured.
- Cache is enabled.

Required response:

```json
{
  "status": "ok",
  "keys_configured": 2,
  "cache_enabled": true
}
```

`keys_configured` must reflect the actual configured count.

## POST /chat

Request:

```json
{
  "session_id": "s-7f3a",
  "message": "What is the capital of France?"
}
```

Optional field:

```json
{
  "system_prompt": "You are a helpful assistant."
}
```

Validation:

- `session_id`: required string, 1–128 characters.
- `message`: required string, 1–4000 characters after trimming.
- Invalid requests return HTTP 422.
- Unknown session IDs start new sessions.

Required response structure:

```json
{
  "session_id": "s-7f3a",
  "reply": "The capital of France is Paris.",
  "metadata": {
    "resolution_source": "LIVE_INFERENCE",
    "model": "gemini/gemini-2.0-flash",
    "latency_ms": 812,
    "input_tokens": 42,
    "output_tokens": 9,
    "key_id": "key_1",
    "fallback_attempts": 0
  }
}
```

The example values are illustrative, not hardcoded.

Required metadata rules:

- `resolution_source`: exactly `LIVE_INFERENCE` or `LLM_CACHE`.
- `model`: actual LiteLLM model name.
- `latency_ms`: integer, measured server-side.
- `input_tokens`: prompt tokens for this request.
- `output_tokens`: completion tokens for this request.
- `key_id`: successful key identifier or null on cache hit.
- `fallback_attempts`: failed keys before success, or zero on cache hit.

Never return accumulated conversation token totals.

## GET /sessions/{session_id}/messages

Return messages in chronological order.

Required response:

```json
{
  "session_id": "s-7f3a",
  "messages": [
    {
      "role": "user",
      "content": "What is the capital of France?"
    },
    {
      "role": "assistant",
      "content": "The capital of France is Paris.",
      "metadata": {
        "resolution_source": "LIVE_INFERENCE",
        "input_tokens": 42,
        "output_tokens": 9
      }
    }
  ]
}
```

Include all available assistant metadata where appropriate.

Never expose system prompts as conversation messages.

Unknown sessions must return:

HTTP 404

```json
{
  "detail": "session not found"
}
```

# 5. LITELLM INTEGRATION AND KEY FAILOVER

Use LiteLLM as the LLM gateway.

Configure a pool of at least two API keys using:

`LLM_API_KEYS`

Example:

`LLM_API_KEYS=key_value_1,key_value_2`

Never hardcode credentials.

Assign identifiers:

- `key_1`
- `key_2`
- `key_3`, etc.

Implement automatic failover for:

- HTTP 429.
- Provider quota exhaustion.
- HTTP 500.
- HTTP 502.
- HTTP 503.
- Other applicable provider-side 5xx failures.

Expected behavior:

1. Attempt the first available key.
2. Detect eligible failures.
3. Retry using the next configured key.
4. Continue until a request succeeds or the pool is exhausted.
5. Return the actual model response.
6. Record the successful key identifier.
7. Report the number of failed keys.

Use LiteLLM for provider calls and failover functionality. Ensure the implementation actually satisfies the required observable behavior.

Do not fake failover by changing metadata without switching keys.

If every provider fails, return:

HTTP 503

```json
{
  "detail": "all providers unavailable"
}
```

Do not save failed requests to SQLite.

Never expose provider stack traces or API secrets.

`X-Simulate-Failure: *=429`

Supported simulated statuses:

- 500
- 502
- 503

Simulation must be enabled only when:

`ENABLE_FAILURE_SIMULATION=true`

The deployed backend must have this enabled for evaluation.

Required outcomes:

### Test 1

Header:

`key_1=429`

Expected:

- HTTP 200.
- `key_id = key_2`.
- `fallback_attempts = 1`.
- Real LLM answer.

### Test 2

Header:

`key_1=500`

Expected:

- HTTP 200.
- `key_id = key_2`.
- Real LLM answer.

### Test 3

Header:

`*=429`

Expected:

- HTTP 503.
- Exact detail: `all providers unavailable`.
- No new session history records.

Simulation must affect only the current request.

Do not globally disable API keys.

Handle the interaction between caching and simulated failures carefully so failure tests cannot be accidentally bypassed by an existing cached response.

# 7. RESPONSE CACHING

Use LiteLLM's built-in caching mechanism.

Do not replace it with a custom dictionary-only cache.

Allowed backends:

- In-memory.
- Disk.

Do not use Redis or other external storage services.

Cache identity must depend on:

- Model.
- Complete system prompt.
- Full conversation history.
- Current user message.

Do not use session ID alone as the cache key.

## Required caching behavior

First request:

- Cache miss.
- Call the LLM.
- Return `LIVE_INFERENCE`.

Identical first message in a different new session:

- Cache hit.
- Return `LLM_CACHE`.
- Return identical reply text.
- Return stored input and output token usage.
- Set `key_id = null`.
- Set `fallback_attempts = 0`.

A different message must never return an unrelated cached response.

A changed conversation history must produce a different cache identity.

A changed system prompt must also change cache identity.

Cache hits must be faster than live inference.

Ensure cache metadata accurately reflects whether LiteLLM actually reused a response.

Do not infer cache hits solely from response similarity.

Handle database writes safely.
